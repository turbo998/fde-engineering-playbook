# AI 辅助工程方法对比

本文比较的是**开发工作流与工程方法包**，不是酒店业务的 Agent 运行时，也不是完整的 FDE 技术栈。FDE 在此指 Forward Deployed Engineer：围绕具体业务问题，完成澄清、实现、集成、验证和交付。

**证据状态：公开源码与文档研究；尚无本项目的四组实测成绩。** 文档检索基准为 2026-09-29。以下适用性判断是研究者解释，不代表上游承诺、客户采纳证明或性能结论。

## 先区分三个层次

| 层次 | 解决的问题 | 本研究中的对象 |
| --- | --- | --- |
| 开发宿主与模型 | 谁调用模型、读写代码、运行工具 | Copilot CLI、Codex 及固定的开发模型 |
| 工程方法包 | 如何发现问题、制定计划、组织实现和验证 | HVE、Superpowers、gstack；补充 Spec Kit、OpenSpec |
| 被开发的业务应用 | 如何处理风险订单、审批、重排和供应商分析 | 各组独立实现的匿名旅行运营应用 |

方法包不等于业务 Agent。切换开发方法不应同时偷偷更换业务数据、验收标准和应用运行模型，否则无法解释差异来自哪里。

## 核心能力

| 对象 | 源码定义的重点 | 对 FDE 的潜在帮助 | 边界与代价 |
| --- | --- | --- | --- |
| HVE | 上下文、工程标准、组织知识、治理和 RPI 生命周期 | 把调研、决策、实现证据与交付责任连接起来 | 强约定且快速演进；不能当作稳定生产基础平台 |
| Superpowers | 可组合的澄清、计划、实现、审查和验证技能 | 约束“直接写代码”的冲动，强调可检查的任务与完成证据 | 技能文字不是模型必然遵循的保证；不同宿主行为需验证 |
| gstack | 角色化产品/工程流程、浏览器工具、QA 与交付技能 | 同时覆盖问题定义、产品体验和真实浏览器验收 | 不只是 Markdown；工具、操作系统和宿主依赖必须纳入成本与兼容性 |
| 无方法包基线 | 相同宿主与模型、业务任务、工具及中立安全要求，不加载方法包 | 用于观察额外方法的收益与负担，而非预设它一定更差 | 仍可能受模型固有能力影响，必须排除全局技能和历史记忆污染 |

这里的“帮助”是待实验检验的假设。不能据仓库热度、作者叙述或技能数量推导“提高几倍效率”。

## HVE：重用组织知识，而不是强制重复所有阶段

当前公开 RPI 文档强调先检查已有证据是否足够：存在实质缺口才进入 Research，随后按需要选择 Plan、Implement、Review，并把问题路由到 Follow-up。`RPI Agent` 是生命周期入口，不应被简单描述成必然自动串联的多个工作代理。

对 FDE 有价值的不是文档数量，而是能够回答：为什么采用这个方案、依据是什么、谁批准、如何证明需求满足、遗留事项交给谁。使用成本也需要测量，包括上下文负担、维护成本和不必要流程。

上游明确提醒 HVE 快速变化，应把它作为可学习和适配的方法来源，而非稳定生产依赖。研究应固定版本，不能把旧教程的“每阶段强制清空上下文”或“所有任务都先研究”当成当前统一要求。[H1][H2]

## Superpowers：观察实际技能，而不是只读 README

Superpowers 将意图澄清、设计、计划、实现、审查和完成验证组织为可组合技能。它适合研究两个问题：复杂任务是否得到更明确的边界，以及“已完成”是否真的附带新的验证证据。[S1][S2]

固定版本中，README 的简述与 `writing-plans` 技能及发布说明存在细节差异：后者强调接口、独立可测交付和可检查结果，不把计划当成提前写好的完整代码实录。因此采用行为时应以同一版本的实际技能为准，并记录真正触发了哪些技能。[S3][S4]

它不能替代后端授权，也不能保证生成代码正确。应用中的金额限制、审批版本和禁止外发必须由代码及独立测试验证。

## gstack：产品与浏览器工作流，不是完整云平台

gstack 包含本地浏览器执行组件，不能被描述成“仅若干提示词”。其问题发现、工程计划、QA 与发布流程覆盖不同职责；有些步骤会提交、推送或创建 PR，实验必须明确限制这些副作用。[G1][G2]

所研究版本包含 Codex 原生宿主路径，未在宿主注册表中提供完整 Copilot 集成。通用 instructions 指引不等于完整技能、浏览器和审查能力。外部 review 还可能依赖另一套已鉴权 CLI，必须逐项检查，而不是静默跳过后声称“完整原生”。[G3]

本项目因此把 gstack 放在原定第四组的**Codex 原生观察轨道**；它不是新增第五组，也不与 Copilot 组混做方法增益排名。

## 两个规格驱动补充

| 项目 | 独特视角 | 本研究中的用途 |
| --- | --- | --- |
| GitHub Spec Kit | 项目原则、规格、计划、任务、实现，以及规格与代码的收敛检查 | 研究需求到实现的可追踪性；只做文档对照 |
| OpenSpec | 当前规格与在途变更分开，用需求增量描述增加、修改、删除和重命名 | 研究存量系统演进及交接；只做文档对照 |

Spec Kit 的价值不只是生成一次规格，而是把未收敛工作重新暴露出来。[K1] OpenSpec 的增量规格提供了描述既有行为变化的方法，而不必每次重新编写整份系统规格。[O1]

没有把两者额外加入运行对照，是为保持首轮范围明确，而非认定它们较弱。

## 公平比较的实验分层

| 轨道 | 原定组 | 可以回答的问题 | 不能直接声称 |
| --- | --- | --- | --- |
| 预期受控轨道 | baseline、HVE、Superpowers；统一 Copilot 开发条件并验证兼容性 | 本次任务在这些固定条件下表现有什么不同 | 单次开发已经证明某方法具有普遍因果优势 |
| 原生观察轨道 | gstack + Codex | 该原生组合能否交付，依赖和可观察效果如何 | 与不同宿主的差异全部来自方法包 |
| 相同应用运行条件 | 所有可执行成品使用同一运行模型、数据与评测接口 | 不同成品满足业务合同的程度 | 运行表现能够单独解释开发方法的效果 |

四组必须分别从业务空白种子工程实现。可以共享 API 契约、模型传输、模拟业务服务和评测器，不能共享已经完成的审批逻辑、状态机或 Agent 提示词。

每组一次独立开发、每场景三次重复运行属于探索性研究。运行重复不能补足独立开发样本；不应制造显著性、稳定性或行业排名。失败、超额、未运行和不支持都应留在结果中。

## 选型原则：先提出假设，再看证据

需要团队规范和可追溯交付时，可优先检验 HVE；需要明确的任务纪律和完成验证时，可检验 Superpowers；重视跨角色产品流程与浏览器验收时，可检验 gstack。需求与实现长期漂移、或存量系统变更较多时，进一步研究规格驱动方法。

这些不是实测推荐榜。真正选型还要检查宿主支持、现有技能冲突、人工介入、工程质量、操作体验、用量以及维护负担。关键审批失败不能被较快速度或漂亮界面抵消。
