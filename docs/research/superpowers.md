## 从模糊意图到可检查任务

brainstorming 关注用户要解决的问题和边界；writing-plans 以批准规格为输入，先确定文件/职责和任务接口，再安排失败测试、验证失败、最小实现、验证通过和提交。重点是执行者不能自行猜测的决定：哪些签名、数值、断言和依赖，而不是长篇复述程序。

当前计划任务边界以“可独立测试且值得新鲜审查”为准，setup/配置/文档合并进所属交付，不机械拆成微任务。计划包含 Global Constraints 和 Review Focus，把规格没有逐字列举但真实使用容易遇到的输入条件放入测试。

实际技能有比例自查：如果计划远长于规格且大多是实现代码，就失去计划作用。也会检查规格覆盖、步骤可判定性、跨任务类型一致和 Review Focus。它可以提高决策密度，也可能增加前期投入；本实验需要同时记录首个可运行时间和最终修复量，不能只报后者。

## 两种执行路径不是同一干预

v6.4.1 起，Native `executing-plans` 是当前会话逐项完成计划，最后有整支分支的新鲜评审；subagent-driven 则每任务由新执行者及评审工作。README 和发布记录都明确两者不同 [S1][S3]。

受控实验必须预先选择路径，并明确子代理、评审模型、上下文和用量怎样计入。不能让 HVE 用一种资源条件，而 Superpowers 无限生成额外更强评审者，再把结果只归因于技能。此阶段不替用户选择精确模型或开启代理链。

计划交接中的确认是工程执行授权，不是业务应用 UC03 的批准。即使计划被确认，候选应用仍要独立实现角色/租户/actor 校验、版本绑定与过期失效。两层批准不能混为一谈。

## 对场景的可能价值与风险

UC02 的距离/等级/房型边界、UC05 的未知容量、UC07 的只留草稿，适合显式负例测试。Red/green 可以帮助验证测试真的能发现错误，但公开工程单元测试不能替代私有 holdout。候选可自写测试，独立评测器仍检查服务账本及状态。

如果计划中已包含全部隐藏答案或完整领域实现，比较将变成照抄。共享规格应给行为，不给私有情景期望；每组自己进行实现决策。测试替身需注明，不能将 stub 回复当真实 LLM 推理。

| 采用风险 | 应保留证据 |
| --- | --- |
| 技能自动触发与宿主 hook 不一致 | 实际加载/激活记录，未触发记失败或不支持 |
| 过度拆分导致上下文与评审开销 | 任务数、调用数、返工和人工介入，不只行数 |
| “测试通过”只指局部选中测试 | 完整相关验证命令与退出码；失败不隐藏 |
| 方法与工具默认设置引入其他变化 | 固定版本、tool inventory、模型配置及执行模式 |
| 可选视觉伴侣外部请求 | README 披露默认 logo 版本遥测与 opt-out；实测预先禁用非必要外连 [S1] |
